# Journey

What was done to turn Pitstop into a case study, what broke, and what was
wrong, in order. Pitstop itself was built from August to October 2026; its
own history is in the commits. This log starts when the case-study work did.
The plan is in [docs/planning/](docs/planning/).

## 2026-10-25: What's actually real

The first look at the database was a set of read-only counts: 164 runs
over 11 weeks, 128 days of campaign data, 76 vehicles. I described that as
"11 weeks on a real Google Ads account". **That was wrong.** Pitstop's own
case study already said the ad data is generated by a seeded simulator,
because the developer token never got beyond test access. The runs, the
model calls, the costs and the failures are real; the ads are not.

The lesson: read what the project says about itself before interpreting
its data. Everything since is built on the line between those two.

## 2026-10-26: Back up first, publish second

**The database came first.** It lived on a hosted server whose account had
run out of credit, and with it went the only record of how the system
behaved. It was dumped through a `postgres:16` container, matching the
16.14 server, and the dump was verified by restoring it into a throwaway
container and comparing row counts.

**Then the history, before publishing.** The repo had 217 commits on 6
branches, and making it public exposes all of them, not just the latest
files. No scanner was installed, so a small one was written:
- it takes every value in the local `.env` files and searches every
  commit for that exact value;
- it adds pattern checks for key formats, connection strings, emails,
  phone numbers and ad-account IDs;
- it lists any risky files ever committed;
- it prints only the commit, the file and the kind of finding, never a
  value.

It found nothing that needed rewriting. The only real values were two
public URLs, and every database URL in the tests pointed at a fake host.

**`main` was 176 commits behind the deployed version**, which lived on a
feature branch. That branch was merged into `main` with a merge commit, so
the branch history stays visible.

## 2026-10-26: Private notes in a public repo

**My private working notes were committed into this repo.** They were an
internal handover file, with context that was never meant to be public. I
caught it before writing the README, and removed the file from my local
commits. But those commits had already been pushed. The next push was
rejected, and the merge that resolved it brought the old commits back.
Every branch built afterwards carried them.

**The fix:**
- rebuild every branch on the clean commit underneath that merge (the
  files were identical; only the commit IDs changed);
- delete the GitHub repo and create it again, empty;
- push the clean branches.

A force-push alone would have left the old commits reachable by direct
link.

**Two lessons:**
- **Check the remote before rewriting history.** A local rewrite doesn't
  undo a push.
- **Don't trust `git log -- <file>` to say a branch is clean.** Git's
  history simplification hides one side of a merge when the result is
  unchanged, so that check reported "clean" while every branch still held
  the file. `git branch --contains <commit>` is the reliable check.

## 2026-10-26: The tests didn't pass in a clean clone

On the first run in a fresh clone, the backend's 388 tests passed, but
**17 of the 22 frontend checks failed and the typecheck crashed.** Both
had the same cause.

- **The cause:** the README installs both packages with npm workspaces
  from the repo root, which moves shared dependencies into the root's
  `node_modules`.
- **The checks** imported Vue from `frontend/node_modules` by file path.
  That folder existed on the original machine only because the frontend
  had once been installed separately.
- **The typecheck:** the hoisted `vue-tsc` picked up the backend's
  TypeScript 7 instead of the frontend's 6.

**The fix:** a helper that looks in both places, and a wrapper that hands
`vue-tsc` the frontend's own TypeScript. A typecheck that exits 0 proves
nothing until it can fail, so a type error was planted in a `.ts` and a
`.vue` file; both failed it.

## 2026-10-26: The numbers, checked against the story

Ten plain SQL queries, later twelve, run by one script against the frozen
snapshot. Two runs give byte-identical output. Several numbers in the
original write-up changed:

- **"About 6 model calls per run" became 7.3 (6 to 10).** That's measured,
  but only for runs after tracing began on 28 September.
- **"About 18 calls before" can't be checked.** It predates tracing, so the
  case study now says it's a recollection.
- **"The flag rate sat near 33%" holds:** 32.5% in August, 29.6% in
  September. Counted over final versions only, the rate fell from 95% to
  36%, which is the point of that lesson.
- **The approval fix's go-live date comes from the data**, the first
  severity-tagged review, rather than from the commit, because backend
  commits were synced in batches. It matches anyway: 28 September. Final
  approvals went from 3.8% before to 75.6% after. That's mostly a stricter
  rule becoming a fairer one, not better reports, and the case study says
  so.
- **I got one caveat wrong and corrected it.** I wrote that the critic's
  grade and its approval are "separate". In fact a D or F grade always
  blocks approval. They differ because grades are given on every draft,
  and approvals count only final versions.

**The raw failure messages couldn't be published.** Some carried provider
account IDs, trace IDs and billing details. The query maps each message to
a cause category, and the mapping is the whole classification.

## 2026-10-26: A demo that can't spend money

A read-only demo of the real run history, in three capped containers.
Zero spend comes from four independent layers:
- no paid API keys on the server;
- no crontab (Pitstop has no scheduler inside the app);
- the demo account is read-only;
- `verify.py`, which checks all of that against the running stack.

**The data is cleaned first,** by a SQL script that aborts if anything it
should remove survives. Each of its checks was shown to fail with its
cleaning step removed.

**The browser check caught what the cleaning missed.** The System Health
page showed raw provider error text from two refused runs: an account ID,
a spend figure, and "account overdue". The evidence had already mapped
those to categories, but the demo's own copy of the data hadn't. Now it
does, with a check that blocks them from coming back.

**A false pass, caught.** One of `verify.py`'s deliberate breaks, adding a
key to the demo's settings, at first "passed". The shell had silently
failed to recreate the container (zsh doesn't split `$C` into words), so
the break never happened. It was spotted because the container's
variable count hadn't changed. Rerun properly, the break failed the check
as it should.

## 2026-10-26: CI

GitHub Actions runs:
- the install, as the README does it;
- the backend build and tests;
- the typecheck, the frontend checks and the production build;
- a check that every evidence query has its committed result and every
  link in the case study resolves;
- a build of the demo images.

Every step was run first in a fresh clone of the committed code. The
evidence check was broken on purpose twice (a missing result, a bad link)
and failed both times. CI can't rerun the queries or start the demo,
because the snapshot stays private; `verify.py` covers the running demo.
